# AAMR-K1 (EXP-PLACEBO-0): is it the memory's content, its format, its domain, or just extra text? Mechanical record: code, specification, stimuli, outcomes and the generated report

**Status: completed on 2026-11-14 (run end 07:04 UTC). Result: nothing decided; no contrast detected an effect of the memory content at the
registered 10 percentage-point level, and no contrast excluded one except as stated below. Development-scale: 148 tasks, one
benchmark, one local model. The mechanical closure check passed.** This directory is the **mechanical** record only: the frozen
specification, the executor's code and tests, the prepared stimuli, per-episode checker outcomes, and the report generated by the
analysis code. **No interpretation is included**: a scientific audit of K1 by Fable 5.2 is a separate piece of work and, when it is
finished, a separate document and pull request. The specification, decision records and report are in **Polish**, as written by the
executor (Claude Opus 5.5) and the specification editor; this README is the English summary.

## What K1 asks
The historical gain of the memory arm over no memory (M against N) is 8.1 percentage points on these tasks. K1 asks which part of it
comes from what: five arms of a Qwen2.5 14B agent on 148 BFCL multi-turn tasks (Vehicle Control, file system, travel):

| Arm | The block shown before each turn | Differs from the step before by |
|---|---|---|
| N | no block | |
| P | neutral prose about geology and botany, token count matched to the M block of the same turn | the presence of text under the memory header |
| X | success traces from **another domain**, same number as M | trace format and foreign tools |
| S | **random** traces from the same domain, disjoint from those M retrieves for the task | domain knowledge |
| M | the real memory (raw success traces, retrieved by the lexical kernel, as in NIGHT-2) | the retrieval of traces for the task |

Three contrasts M-P, M-X, M-S with the registered threshold of 10 pp (`SPEC_K1_PLACEBO_v1.0.1.md`, sections 3 and 8): at most
three sampled blocks (temperature 0.7, 148 tasks x 5 arms each) and one block A at temperature 0 (N, M, P). The specification says
before the run that K1 is a *bounding and calibrating* experiment: with 148 tasks it detects an effect of 10 pp in about 64% of runs
and cannot separate components if effects are of the historical size (3 to 9 pp).

## Result (the generated report `report/K1_RAPORT.md`, copied here, not recomputed in full)

| Contrast | Estimate (pp) | Interval | State by the registered reading code |
|---|---|---|---|
| M - P | +2.7 | [-6.0; 11.4] | V4: not decided, the interval holds both 0 and 10 pp |
| M - X | +4.1 | [-4.4; 12.5] | V4: not decided |
| M - S | -0.2 | [-8.1; 7.7] | V5: no effect detected; effects above 7.7 pp are not supported, so this component does not give the whole historical 8.1 pp. **The length flag (LEN) is set**: a difference in block length can explain it; it is not attributed to memory content |

Solve rates over the three sampled blocks (444 episodes per arm): N 32.9%, P 32.0%, X 30.6%, S 34.9%, M 34.7%. The report adds a
dependence between M and S through shared traces (rho~ = +0.030, p = 0.016), a domain dependence of M - S (Vehicle Control layer
of E3: 16.7 pp, the 95% interval excluding 0 with the opposite sign), and **an unmet drift control of block A** (agreement of M with
NIGHT-2 below the threshold: 83 of 88 and 55 of 60); states from the sampled blocks stay valid per the specification.
The specification's own rule of interpretation (D1) is quoted at the top of the report: a result below the 10 pp threshold does
not show that memory has no benefit.

**Independently re-derived here (2026-11-14), from the published `eval/S1..S3.jsonl`:** the solve counts per arm (N 146, P 142, X 136,
S 155, M 154 of 444) and the descriptive differences P - N = -0.901 pp and M - N = +1.802 pp equal the report's. The contrasts, their
intervals, the dependence estimates and the states were **not** re-derived (they need the analysis code and the full run).

## Not published, on purpose
- **The raw run** (`attempts.jsonl` 293 MB, `responses.jsonl` 15 MB, state and logs; 326 MB): too large and not cleared for publication; only its SHA-256
  is in `out/raw-freeze.json`. Nothing in this repository lets a reader recompute those sums or the contrasts from model outputs.
- The original L8 manifest `MANIFEST.json` (it also lists the Python start-up files of the machine); its hash mapping is published, with relative
  paths, as `meta/manifest-L8-files.json`. The published copies of all 29 files it pins were checked against it: 29 of 29 equal.
- The coordinator's integration files and registry snapshots, the closure copies, and the pilot K1-CAL-NM (its sealed results were never opened; only a hash is in `FREEZE.json`).
- Any interpretation by Fable 5.2 and its blinding material.

## Reproducibility and limits
- **K1 cannot be rerun from a clean clone**: it needs the local Ollama model (digest `7cdf5a01...`), the pinned BFCL checkout, NIGHT-2's raw
  responses (it reads their token counts) and the coordinator's wrapper. The executor code and tests keep the absolute Windows paths of the
  machine that ran them (see the erratum). The offline tests `executor/tests/run_tests.py` are not part of the repository's CI.
- `meta/manifest-L8-files.json` shows `status_at_preparation: "PREPARED, NOT FROZEN"`: that is the text the manifest carried when it was written, before the
  owner's decisions closed; the closure check records that the manifest was unchanged at the start of the run and at the end.
- The report's reading ("odczyt") is produced by registered code (`k1_v04_reading.read`); the states V4 and V5 are defined in the specification (section 8).
- One benchmark, one model, 148 tasks, one temperature regime in the sampled blocks. K1 was designed to bound, not to confirm.
- Builds on [../aamr-night2/README.md](../aamr-night2/README.md) (the memory arm M is NIGHT-2's R+).
