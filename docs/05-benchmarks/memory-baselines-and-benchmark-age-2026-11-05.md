## Are the old GPT-4-era comparisons current?

The model labels describe **historical published configurations**. They do not measure today's versions of Mem0/Zep/etc. with a current backbone. GPT-4o-mini results are useful for calibrating task difficulty and studying controlled mechanisms, not for stating present-day commercial superiority. The benchmark authors' [repository](https://github.com/HUST-AI-HYZ/MemoryAgentBench) records a May2026 GPT-5-mini update; the [v4 paper](https://arxiv.org/abs/2507.05257v4) is dated28June2026. Neither amounts to a November2026 same-model competition against our candidate.

The owner mentioning GPT-6 does not change the existing inference authorization: API workers remain **DeepSeek V4.1 Flash only**, plus installed local Qwen. No GPT model, Pro model or judge has been invoked. A matched comparison can hold Flash fixed across memory-on, memory-off and a pinned competitor; it need not buy a different brand's newest model. No benchmark result for an untested contemporary model is inferred from its name.

## Is MemoryAgentBench still useful?

Our assessment: retain its counterfactual fact-update/multi-hop slice as a **targeted regression test**, and stop presenting its old systems table as a current leaderboard. Its100questions share one public history, now repeatedly used by us for development. It does not measure centuries of retention, natural free-prose learning or broad agent usefulness. Making a model newer does not remove those construct and contamination limits.

Two newer primary-source directions already in the source catalog are relevant, rather than another self-authored easy slice:

- [LongMemEval-V2 official repository](https://github.com/xiaowu0162/LongMemEval-V2): 451curated questions, web/enterprise trajectories, up to115Mtokens, workflow/gotcha/premise-awareness tasks and an explicit `no_retrieval` baseline; an August2026 update is recorded. It measures experience use and query latency. We have inspected sources, **not executed or passed this benchmark**. Changing the fixed reader/scoring would need a labelled adapted protocol; its default GPT judge is not authorized.
- [MemoryArena authors](https://memoryarena.github.io/): multi-session tasks couple earlier actions/feedback to later decisions across web, planning, search and reasoning. The official code is labelled a preview with environment setup requirements. It is closer to agent utility; **not executed/passed here**, and source inspection is not reproduction.

Next admissible comparison: freeze the same allowed reader, information cutoff, questions, decoding, memory context ceiling and deterministic score where valid; run no memory, ordinary retrieval and our candidate, with a pinned competitor if compatible. Charge ingestion, failed attempts, query work and context separately. Include a different external task and fresh unused cases; do not silently relabel published public data as a sealed test. Preserve every historical negative result. The existing #51 comparison task owns this gap; no additional unexecuted experiment or paid-cap extension is created by this note.

## Could the small-model result be fitting the test?

**Yes: benchmark-specific development is a material, unresolved risk; its magnitude is unmeasured.** The100public MAB questions have repeatedly informed diagnosis and pipeline changes. They are now a development set. The H1 public splits also informed successive changes, even if named validation. A prior protocol/raw-output freeze prevents rewriting a run after scoring; it does not erase exposure from preceding runs or turn repeated development into held-out confirmation.

Two different claims must remain separate. Mechanical reconstruction checks that expected answers/terminal values are not directly supplied to path selection, and targeted searches found no branches on the known failing H1 case IDs in the reviewed runtime/candidate paths. That is bounded leakage/implementation evidence, not a proof against semantic leakage or author-guided selection. The mechanism can still be adapted to the benchmark's fact syntax, relation vocabulary, explicit overwrite policy and available question styles. A new safe exact-only cache also has not independently reproduced the old capture efficiency. No generalization gap can be estimated from the existing55/59development scores.

The tested unit is a small model **plus** derived representation, available executable paths and code execution. Good performance is an engineering signal about that combination; it is not the standalone14B model outperforming large models. The same graph can constrain both readers and make their scores close without validating the representation or proving comparable general ability.

A credible next evaluation must freeze **all** of capture, parsing, cache policy, source selection, prompts, budgets, model identity, scoring and stopping rules before processing unused questions/labels. Prepare a different external dataset without inspecting labels to choose cases, isolate the source state, include memory-off plus a strong ordinary-retrieval baseline, report every selected question and failure, and disclose public-data/pretraining contamination uncertainty. A benchmark inspected for task forms is not the strongest sealed evidence. If results trigger changes, retain the untouched result and label that set as development for later runs; do not keep tuning until the same test turns green. One fresh transfer run would strengthen the case, not establish universal memory.
